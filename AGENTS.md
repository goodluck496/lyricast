# AGENTS.md

## Общие правила
0. Перед началом генерации кода прочитайте `AGENTS.md`. Если в нем есть неясности, задавайте вопросы и отрази то что прочитал вкратце в начале ответа.
1. Всегда отвечайте **на русском языке**.
2. Проект — монорепозиторий. Электронная оболочка (Electron) — базовый способ отображения интерфейса.
3. Соблюдайте принципы SOLID, DRY, KISS и избегайте излишних костылей.
4. Избегайте `type assertion` (`as ...`) без строгой необходимости — выбирайте типы или вспомогательные функции, чтобы компилятор выводил корректные типы сам.
4. Минимизируйте дублирование и чрезмерное упрощение кода. Не удаляйте существующий код без критической необходимости — при временном отключении комментируйте и поясняйте «почему».
5. Используйте общепринятые паттерны проектирования, не добавляйте `setTimeout` без веской причины и не применяйте `::ng-deep` в стилях Angular.
6. Если твои правки будут менять структуру или паттерны, то обязательно создай PROGRESS.md чтобы потом можно было отследить изменения и внести в AGENTS.md.

## Архитектура и основные точки интеграции
- UI построен на **Angular 20** с API, соответствующим этой версии.
- Основной процесс: Electron + Angular. Фронтенд общается с Electron через:
  - preload-скрипт `apps/electron/src/app/api/main.preload.ts`;
  - `postMessage`;
  - пользовательский протокол `apps/electron/src/app/api/svc.protocol.ts`.
- Приложение поддерживает несколько окон Electron и координирует их через стор `libs/common-browser/src/lib/store/casting-flow.ts`.

## Структура приложений
- `apps/browser` — основное Angular-приложение, запускаемое внутри Electron.
- `apps/dictionary-client` — специализированный Angular клиент для словарей/справочников.
- `apps/electron` — исходники основного процесса Electron и preload-скриптов.
- `apps/workers` — каталог с воркерами (каждый воркер — отдельное приложение/папка).

## Структура библиотек
- `libs/common` — платформенно-нейтральные утилиты и типы.
- `libs/common-browser`, `libs/common-electron`, `libs/common-workers` — платформенные наборы helpers.
- `libs/domains` — NestJS-домены/бэкенд-логика (исполняются воркерами).
- `libs/entities` — типы и DTO, общие для фронта и бэка.
- `libs/features` — Angular-фичи (новые страницы добавляем сюда как `angular:library`).
- `libs/openapi` — клиентские и серверные артефакты OpenAPI.
- `libs/shared-browser` — data-access и другие browser-specific Angular libs.
- `libs/styles`, `libs/svg-icons`, `libs/ui-lib` — дизайн-система, иконки и UI-компоненты.
- `libs/worker-kit` — регистрация и вспомогательные утилиты для воркеров.

## Организация функциональности
1. **Новые страницы** создавайте как `angular:library` фичи в `libs/features`.
2. **Воркеры**:
   - Исходники — в `apps/workers`.
   - Регистрируйте их в `libs/worker-kit`.
   - Добавляйте команды запуска в `package.json`.
3. **Фронт ↔ бэк**:
   - Низкоуровневые сервисы данных — `libs/shared-browser/data-access` (Angular libs).
   - Контракты и типы обмена — `libs/entities`.
   - NestJS-домены и бекенд-логика — `libs/domains`. Их исполняют воркеры.
4. **UI-компоненты**:
   - Используйте PrimeNG и Angular Material/CDK. Для гайдов смотрите `llm-docs/` (особенно `llm-docs/primeng-llms-full.txt`).
   - Нельзя изобретать кастомный компонент/директиву, если аналог есть в `llm-docs/primeng-llms-full.txt` либо `libs/ui-lib`.
   - Компоненты должны быть максимально декомпозированы.
   - По возможности избегайте `@Input/@Output` — предпочитайте DI и общие сторы/сервисы.
5. **Логика компонентов**:
   - В Angular-компонентах держите только отображение. Всю бизнес-логику выносите в соседние сервисы или слой выше.

## Данные, инструменты и генерация API
- Общие/кросс-платформенные утилиты — `libs/common`.
- Специфические наборы helpers:
  - Electron — `libs/common-electron`.
  - Workers — `libs/common-workers`.
  - Browser — `libs/common-browser`.
- Инструменты сборки, преобразователи, хелперы запуска — в каталоге `tools/`.
- OpenAPI-генерация для внешних сервисов:
  - Клиентские артефакты — `libs/openapi/client`.
  - Бэкенд-артефакты — `libs/openapi/backend`.

## Работа с данными и БД
- Воркеры сейчас работают с JSON в `USER_ASSETS`, но целевая модель — SQLite через **Drizzle**.
- За примером взаимодействия с БД смотрите `libs/domains/asset-domain/src/lib/asset-domain.service.ts`.

## Практики разработки
1. При проектировании решений предлагайте уже существующие внутри проекта подходы — избегайте «велосипедов».
2. Избегайте платформенных хаков и нестандартных решений без необходимости.
3. Для взаимодействия роутов, кешей и DI пользуйтесь встроенными механизмами Angular.
4. Везде, где это возможно, проверяйте существование методов перед вызовом, если используете нестандартные API (например, у кастомных стратегий роутинга).
5. Тестируйте критические сценарии в production-окружении — поведение DI и интерцепторов может отличаться.
